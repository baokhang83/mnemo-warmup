Spring Boot on distroless with mnemo-warmup

Extract the layered JAR in a multi-stage build, run it on gcr.io/distroless/java21-debian12 (no shell), and let the injector add the trainer and the fetch step. Nothing in the generated pod needs /bin/sh.

1. Build the image

An archive remembers the JAR files it was trained on, so the trainer and every pod must run identical files at identical paths. Spring Boot 3.3+ can extract its JAR at build time:

# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
COPY src src
RUN --mount=type=cache,target=/root/.m2 \
    mvn -B -ntp -DskipTests package \
 && java -Djarmode=tools -jar target/app.jar extract --destination /out

FROM gcr.io/distroless/java21-debian12
COPY --from=build /out /app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

The complete file is examples/spring-boot/Dockerfile.distroless.

2. Annotate the Deployment

spec:
  template:
    metadata:
      annotations:
        warmup.mnemo.io/enabled: "true"
        warmup.mnemo.io/store: "oci://registry.example.com/team/app-warmup"
        warmup.mnemo.io/exit-mode: "spring-refresh"
    spec:
      containers:
        - name: app
          image: my-app:1.0
          command: ["java"]
          args: ["-Xmx512m", "-jar", "/app/app.jar"]

The injector needs an explicit java [options] -jar <jar> [args] in command and args. If the Java command comes from the image’s ENTRYPOINT, supply it with warmup.mnemo.io/command: '["java","-jar","/app/app.jar"]'. Launches with -cp and a main class are not supported. A changed JVM option is a new fingerprint, so a new archive is trained.

3. Preview, then deploy

helm template my-app ./my-chart --namespace my-namespace \
  | mnemo-warmup inject --namespace my-namespace --preview

helm upgrade --install my-app ./my-chart --namespace my-namespace \
  --post-renderer ./scripts/mnemo-warmup-inject \
  --post-renderer-args=--namespace=my-namespace

The preview lists the container, JAR, store, trainer mode and what the trainer copies from your workload by name only; it never prints a value. Review it: the trainer starts your application for real with that configuration. Helm 3 only; with Helm 4 pipe helm template | mnemo-warmup inject | kubectl apply -f -.

Why no shell is needed

Every generated container runs mnemo-launcher, a static Go binary: install copies the tools, fetch looks up the archive (a failure is logged and exits 0), and exec asks the tools for the final command and replaces itself with it, so java is PID 1 and gets SIGTERM directly. It finds java the way your command would: an explicit path, then PATH, JAVA_HOME, common JDK locations.

Optional: no init containers

Add warmup.mnemo.io/tools-delivery: "image-volume" on Kubernetes 1.33+ with a supporting runtime. See the measurement.

What was verified, and limits

  • scripts/e2e-kind-inject.sh runs this path on kind with Helm 3 on both a Temurin and a distroless Java 21 image: preview, first start, asynchronous training, cache hit, update and rollback, corrupted archive, stopped registry, removal.
  • scripts/verify-image.sh checks the launcher on gcr.io/distroless/java21-debian12 (install, train, push, fetch, corrupt archives, UTF-8 arguments, exit status, SIGTERM).
  • Java 21 or newer must be in the application image. Cache files are mode 0600 and owned by the user that ran fetch, so run the app as that user.
  • Annotation path run end to end on JDK 21 (AppCDS) only; JDK 25 AOT is covered through the Helm chart and the GKE study. Alpha.
