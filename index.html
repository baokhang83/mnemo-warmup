Automate AppCDS & Project Leyden AOT caches on Kubernetes

mnemo-warmup trains a class-data archive once, inside your cluster, stores it in an OCI registry, and gives it to every replica of an unchanged JVM application. A pod starts from the archive only when it fits its launch exactly; otherwise it starts the ordinary way. No GraalVM, no application code changes.

When to use mnemo-warmup

Different tools shorten JVM start in different ways. This matrix is a summary for orientation, not a benchmark.

ApproachWhat you getWhat it asks of youWhere it hurts
GraalVM Native ImageThe fastest cold starts and smallest footprint of these options.A native build in CI; reachability metadata (reflection, proxies, resources) available at build time.Closed-world compilation: some dynamic JVM features are restricted, and the native binary needs its own build, test and debug path.
CRaC (checkpoint/restore)Restore a warmed-up JVM instead of starting one.A CRaC-enabled JDK, checkpoint hooks for open resources, and a checkpointing step in your pipeline.Restore typically needs extra Linux capabilities in the container, and state must be made safe to snapshot. Check your platform’s policy.
Manual AppCDS / Leyden in CIThe same JVM archives, built in a Dockerfile stage.A multi-stage Dockerfile and a training run per application, kept in step with every JDK and JAR change.Training in CI lacks the cluster’s real config; the archive must match the exact JDK build, JARs and paths.
mnemo-warmupAppCDS (JDK 21+) or Leyden AOT (JDK 25) archives, trained in the live cluster, shared through an OCI registry.No code change: three annotations. An explicit java -jar launch and identical JARs in trainer and pods (Spring Boot: extract the JAR when building the image).One extra real startup in a trainer pod; a registry to run; gains only where start is class loading (neutral on Jenkins, none on SonarQube); alpha.
Pick mnemo-warmup when startup is dominated by class loading in a framework-heavy service, you can’t or won’t go native, and you’d rather not run a CRaC checkpoint pipeline. Pick another when you need sub-second starts at any cost (native), or your start is dominated by initialization work (database, caches), which no class archive removes.

Three annotations

spec:
  template:
    metadata:
      annotations:
        warmup.mnemo.io/enabled: "true"
        warmup.mnemo.io/store: "oci://registry.example.com/team/app-warmup"
        warmup.mnemo.io/exit-mode: "spring-refresh"   # or http-probe, plus warmup.mnemo.io/probe-url
helm upgrade --install my-app ./my-chart --namespace my-namespace \
  --post-renderer ./scripts/mnemo-warmup-inject \
  --post-renderer-args=--namespace=my-namespace

Alpha: options, annotations and the manifest format may still change. Not verified: live EKS/ECR, Helm 4, remote-registry scale-out beyond the GKE study.

FAQ

Does Project Leyden AOT work with Spring Boot on Kubernetes?

Yes, on JDK 25, where mnemo-warmup trains a Leyden AOT cache in a single step. The GKE benchmark ran Spring Boot sample applications and ThingsBoard CE with AOT archives on Debian OpenJDK 25.0.4.1. On JDK 21 to 24 it uses AppCDS instead. The annotation path was run end to end on JDK 21 only; the Helm-chart path covers both. The project is alpha.

How does mnemo-warmup handle distroless images without a shell?

Every container the injector generates runs a static launcher binary (mnemo-launcher), not a shell script, so gcr.io/distroless/java21-debian12 works. The launcher replaces itself with java, so the JVM stays PID 1 and receives SIGTERM directly. The image still needs Java 21 or newer.

What happens if the OCI registry goes down?

The pod still starts. fetch logs the reason and exits 0, and the application starts without an archive. In the end-to-end test with the registry stopped, pods became Ready about 14 to 15 seconds after deletion, which is how long fetch takes to give up. Missing pull Secrets and unsupported image volumes are deployment errors that this fallback does not cover.

Do I need to change my application code or switch to GraalVM?

No application code changes. You add three annotations (enabled, store, exit-mode) to the Deployment pod template. The container must launch with an explicit java -jar command and run identical JAR files in the trainer and in every pod; for Spring Boot that means extracting the JAR when you build the image.

Does it work with Helm 4?

Not verified. The post-renderer here is a script path, which Helm 3 accepts; Helm 4 expects a plugin and none is shipped yet. With Helm 4, render and inject in a pipeline: helm template | mnemo-warmup inject | kubectl apply.
