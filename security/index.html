mnemo-warmup / Security

Security model

What mnemo-warmup can touch in your cluster, how an archive is validated before use, and what happens when something is wrong. Written for the platform engineer deciding whether to put a third-party post-renderer in a deployment path.

Alpha software and not independently audited. This page describes behaviour documented and tested in the repository; read the source and the preview output for your own review.

Kubernetes RBAC scope

  • The injector is offline: it reads rendered YAML on stdin, writes YAML on stdout, and contacts no cluster.
  • Per opted-in workload it generates one CronJob, ServiceAccount, Role and RoleBinding, named after the Deployment plus a short hash.
  • The Role grants get, create, update and delete on leases only, in the workload’s namespace. No Secrets, pods or cluster-wide access.
  • The trainer starts your application with copied environment variables, envFrom references, volumes and mounts, security context, pull secrets, node selector, tolerations and affinity. It therefore holds whatever your app holds. The preview lists these by name only; review it.

Lease locking

Before training, the trainer takes a Kubernetes Lease named after the fingerprint, so two trainers never train the same archive. A lease left by a crashed trainer expires on its own (kubectl get lease | grep mnemo-warmup). The CronJob does not overlap runs and stops a run after one hour.

Archive integrity

  • Archives are OCI artifacts tagged by fingerprint: JDK build, classpath JAR contents and JVM options. A changed option or image is a different archive.
  • fetch verifies the digest before use. In the end-to-end test, 4 KiB of a stored archive were overwritten with random bytes at the same size: the pod rejected it and started uncached and Ready.
  • Before adding the JVM flag, run compares the manifest with this exact launch: JDK build, JVM options, classpath content, JAR modification times and training directory. Any mismatch starts java as given and logs why.
  • The CLI installer’s SHA-256 checks detect corrupt or mismatched downloads; they do not authenticate a compromised release source.
  • Archives hold class metadata for your application. Treat the archive repository like any registry holding application artifacts: restrict who can push.

Credentials

  • Pull and push credentials are separate Secrets (or roles). A read-only credential cannot overwrite archives. Image-pull credentials are not reused for the archive store.
  • ECR via IRSA: short-lived web-identity credentials, cached and refreshed; none written to logs or errors. See EKS and ECR.
  • With a pull Secret or node cache, even image-volume delivery keeps a fetch init container so credentials and cache identity stay out of the application container.
  • Optional node-local cache: HTTPS only, a CA from a ConfigMap, a projected service-account token with its own audience; it follows at most one same-origin redirect, never forwards credentials to another host, and verifies the client’s registry proof on every request including hits.
  • Do not put credentials under shared CI caches or build files.

Fail-safe behaviour

Failures looking up or validating an archive never stop a pod; it starts the ordinary way and its log says why.

SituationWhat happens
No archive yetfetch: no usable archive; the app starts uncached.
Registry unreachable or login refusedfetch logs and exits 0; Ready about 14–15 s later in the end-to-end test.
Archive damagedRejected by the digest check; uncached start.
Image has no Java, or older than 21The launcher skips the tool; your command runs unchanged.
run helper stallsStopped after 60 s; your command runs unchanged.

Not covered by the fallback

  • A pull-secret or push-secret that does not exist in the namespace.
  • The tools or application image cannot be pulled.
  • With tools-delivery: image-volume, a cluster or runtime without image-volume support: the pod stays in ContainerCreating.
  • An application command that is wrong in the first place.

Removing it

Remove the annotations (or set enabled to "false") and render again; the original command returns and, with Helm, the generated CronJob, ServiceAccount, Role and RoleBinding are pruned. Archives stay in the registry until your retention policy removes them.
