GKE benchmark: Leyden AOT on JDK 25, four workload tiers

How much sooner do pods become ready when each starts from a trained Leyden AOT cache, from one pod up to a nine-pod autoscale burst? Method, numbers and every caveat the study recorded.

One trial per cell, descriptive values only. These are not confidence intervals and not a prediction for your application.

Setup

  • Cluster. A fixed single-node amd64 GKE Standard cluster, one 12-vCPU, 64-GB E2 node, node autoscaling disabled so provisioning stays out of the timings. Workloads used an HPA (min 1, max 9) with Metrics Server 0.9.1 and CPU-based scaling.
  • Runtime. Debian OpenJDK 25.0.4.1 for all four tiers, Leyden AOT archives trained with spring-refresh. The protocol keeps resources, probes and the database seed matched within a tier.
  • Tiers. Minimal (Spring Web, Actuator), Standard (adds JPA/Hibernate, PostgreSQL, Security, Validation, caching), Larger sample (adds Springdoc, Kafka, RabbitMQ, Prometheus) and ThingsBoard Community Edition 4.3.1.8 as a real heavy application with PostgreSQL. The first three are synthetic.
  • Arms. uncached (no archive); direct (each pod downloads the archive from the registry); cold and warm node cache (the optional node-local archive cache, empty or pre-populated).
  • Topologies. One pod, and an HPA scale-out from 1 to 9 under a tier-calibrated request load.

Reading it: in the three Spring Boot tiers a trained archive shortened app-ready time in every archive arm, by more as the tier grew (standard, one pod: 7.4 s uncached against 3.1 s direct). ThingsBoard shortened by about 9 s for one pod and by 4 to 12 s for nine. The study shows no startup advantage for the node cache over direct fetch for a single pod.

Why Kubernetes 1.33+ image volumes matter

This is a separate measurement, from the kind benchmark, not from GKE. By default each pod runs two init containers before the application: one copies the tools, one fetches the archive. Their own work is small (native fetch about 80 ms), but the kubelet starts init containers one after another, and in a stage-by-stage timeline of the Jenkins runs the pod started the application about 1.75 s later than a pod without them. With warmup.mnemo.io/tools-delivery: "image-volume" the tools are mounted as a read-only image volume, so the install init container disappears, and (with no pull Secret or node cache) so does the fetch init container.

Requirements: Kubernetes 1.33 or later (image volumes are beta) and containerd 2.1+ or CRI-O 1.31+. Without support a pod using the volume does not start, which is why the mode is opt-in. Details: ADR 0012.

Limits and anomalies the study recorded

  • One trial per cell; no variance estimates.
  • Original cells used 128 load workers with a 500m limit; Standard and Larger HPA cells were repaired with 256 workers and a two-CPU limit, so HPA reaction times are not comparable across original and repaired runs.
  • HPA timings from watch receipt can include watch buffering; the HPA-ready times above are erratic (for example ThingsBoard warm-cache: 238 s) and are deliberately not summarised here.
  • Ten connection-refused errors at load start appear in several cells; the logs do not identify the rejecting component.
  • Original Larger direct-fetch and warm-cache primer runs hit registry HTTP 401 responses; repaired cells refresh credentials before each trial.
  • A ThingsBoard first-use nine-pod burst against an empty database raised a bootstrap optimistic-lock conflict; such rounds are excluded and the database is restored before each measured round.
  • Single node, registry in the node’s region, workload and tools images pre-pulled: image pulls and node provisioning are excluded by design.
