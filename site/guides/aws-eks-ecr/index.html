Amazon ECR archive store on EKS with IRSA

Use the pod’s IAM role (IRSA) to log in to ECR, so no registry password lives in a Secret. One pull-only role for the application’s fetch, one push role for the trainer.

Not verified on a live EKS cluster and ECR registry. Unit tests use local fakes for STS, ECR and the registry, and the signing code is checked against AWS’s SigV4 test vectors. Run the checklist at the end on your cluster before relying on it. GKE and AKS workload identity and EKS Pod Identity are not supported yet.

How the login works

  1. EKS injects AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE into a pod whose service account carries an IAM role.
  2. For an ECR host (<account>.dkr.ecr.<region>.amazonaws.com, including ecr-fips and .cn), mnemo-warmup calls STS AssumeRoleWithWebIdentity in the registry’s region.
  3. It signs an ECR GetAuthorizationToken call, caches the login for its roughly 12-hour life, refreshes it five minutes before expiry, and refreshes once if the registry rejects it mid-run.
  4. No credential is written to a log or error message.

A --registry-auth file entry for the registry still wins; with neither a file entry nor a web identity, access is anonymous.

Create two roles

Separate roles mean a compromised application cannot overwrite archives. Trust policy for each role:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::<account>:oidc-provider/<oidc-issuer-host-and-path>" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": { "StringEquals": {
      "<oidc-issuer-host-and-path>:aud": "sts.amazonaws.com",
      "<oidc-issuer-host-and-path>:sub": "system:serviceaccount:<namespace>:<service-account>"
    } }
  }]
}

Pull role permissions:

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
    { "Effect": "Allow",
      "Action": ["ecr:BatchCheckLayerAvailability", "ecr:GetDownloadUrlForLayer", "ecr:BatchGetImage"],
      "Resource": "arn:aws:ecr:<region>:<account>:repository/<archive-repository>" }
  ]
}

The push role adds ecr:InitiateLayerUpload, ecr:UploadLayerPart, ecr:CompleteLayerUpload and ecr:PutImage on the same repository. ECR does not create repositories on push: create <archive-repository> first, with tag immutability off, and check the blob-size limit (archives can reach hundreds of MB).

Attach the roles

  • Application (fetch): annotate the application’s service account with the pull role; leave pull-secret and push-secret empty.
  • Trainer, Helm chart: set trainer.serviceAccount.annotations["eks.amazonaws.com/role-arn"] to the push role.
  • Trainer, injector: the injector generates the trainer’s ServiceAccount and has no annotation for it, so add the role annotation with your own patch after rendering. This is a known limitation.

To act as a role in another account, set MNEMO_WARMUP_AWS_ROLE_ARN; the pod’s role then needs sts:AssumeRole on it. Other variables: AWS_ROLE_SESSION_NAME (default mnemo-warmup), AWS_ENDPOINT_URL_STS and AWS_ENDPOINT_URL_ECR for VPC endpoints.

What happens when it fails

fetch treats every login problem (missing token file, denied permission, STS or ECR down) as “no archive”: it prints the reason and the application starts without a cache, exit 0 (--strict exits 1). Transient errors (connection failures, 429, 5xx) get up to three attempts; permission errors are not retried.

Verify on your cluster

  1. kubectl exec into a pod on the annotated service account and confirm AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE are set.
  2. Run the trainer once and check the archive appears in ECR under the tag fp-<hex>.
  3. Start the application and check the fetch log for Archive: rather than a fetch: note.
  4. Remove ecr:PutImage from the push role and confirm the trainer reports the denial while the application still starts.

Nothing deletes archives: bound growth with an ECR lifecycle policy scoped to fp- tags. See archive retention and the source guide.
